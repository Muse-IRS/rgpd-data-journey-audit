# Platform-first RGPD transition

Status: `FORM / PUBLIC-BOUNDARY-CANDIDATE`

Date: 2026-09-06

Repository: `Muse-IRS/rgpd-data-journey-audit`

## Purpose

This note stabilizes the current framing of the public RGPD / data-rights surface.

The project began with an association-oriented public-interest intuition around **droits aux données personnelles RGPD**. The current construction has evolved toward a broader **Muze-X Lab platform** with domain-based public interfaces, a domain name strategy and a possible enterprise structure.

The association idea is therefore not erased. It is reclassified as a possible separate branch, not as the active default public framing of this repository.

## Current public framing

```text
Muze-X Lab
-> public RGPD Data Journey Audit surface
-> data journey readability
-> data rights understanding
-> practical user orientation
-> possible future public-interest / association branch
```

The public interface should help individuals understand:

- what a site or digital service declares;
- what data may be used;
- where data may circulate;
- which actors or recipients are mentioned;
- which purposes, legal bases and retention periods are declared;
- which GDPR / RGPD rights are presented;
- how the user can act;
- what remains missing, unclear or divergent.

## Central conceptual axis

The development branch keeps the deeper conceptual axis:

```text
institutional abstraction
+ effective rights
+ divergence with reality
```

Public expression must remain simpler:

```text
declared right
-> practical access
-> understandable data path
-> actionable next step
```

## Public wording rule

Use platform-first wording:

```text
Muze-X Lab · RGPD · Data Journey
```

Avoid active association-first wording unless the specific page is explicitly about a separate association branch.

Avoid statements that imply the repository is operated by a legally constituted association unless that legal structure has been created, named and documented.

## What should be promoted from development to public

The following elements are suitable for public adaptation:

| Development element | Public adaptation |
|---|---|
| Abstraction institutionnelle | Difference between declared information and practical understanding |
| Droit effectif | A right is useful when it can be exercised and verified |
| Divergence avec le réel | What is clear / missing / inconsistent / still to verify |
| RGPD Article 15 logic | Practical right-of-access orientation |
| CNIL register analysis | Institutional example, only if phrased cautiously |
| SSF-IRS states | SAT / UNSAT / UNKNOWN public status, not a legal ruling |

## What must stay out of the public repository

The public repository must not contain:

- personal data;
- real case files;
- administrative documents;
- legal claims presented as final rulings;
- private prompts;
- private heuristics;
- private matrices;
- unpublished research protocols;
- backtests;
- sensitive source files.

## Operational transition checklist

Before deploying a wording change:

1. Identify association-first strings in public pages.
2. Replace them with platform-first wording where appropriate.
3. Preserve an explicit separation document for possible association / enterprise branches.
4. Keep the public result useful for individuals.
5. Keep the private construction method outside the public repository.
6. Open a pull request before merge when the change affects public-facing text.

## Stable relation

```text
PRIVATE_METHOD
-> PUBLIC_RESULT
-> USER_UNDERSTANDING
-> ACTIONABLE_RIGHTS
```

The public layer is not a verdict engine. It is an intelligibility and orientation surface.
